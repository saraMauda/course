## 🌟 הקדמה

Skills הם "המגניבים החדשים בשכונה" – כולם משתמשים בהם, מדברים עליהם, ומעבירים אליהם יותר ויותר אחריות. הרעיון: לקחת **משימות חוזרות שדורשות מומחיות, ידע או תהליך עבודה**, ולארוז אותן כך שהאייג'נט **נזכר** בהן ומשתמש בהן **רק כשצריך**.

שני מפתחים מ-Anthropic – החברה שהגדירה את התקן – הציגו את הקונספט בהרצאה: **Don't Build Agents, Build Skills.** כלומר Skills כתחליף (ובמידה מסוימת: השלמה) לסוכנים כבדים. הם צודקים בחלק גדול: הרבה "אייג'נטים" הם בעצם אוסף מיומנויות + Tool Calling.

**Skill = Prompt Engineering + Function Calling**, ארוזים בתקן תיקיות.

> **משפט עוגן:** אין קסם. Skill הוא קטלוג שמוגש למודל, ו-Tool שמחזיר הנחיות.

## 📌 מושגים ועקרונות

### Skill
תיקייה עם קובץ `SKILL.md` שמלמד את האייג'נט לבצע משימה ספציפית – מתי להשתמש בה, ואיך.

### Progressive Disclosure
חושפים מידע **שכבה אחרי שכבה**, לפי הצורך. אותו עיקרון עיצוב של ממשקים – על טוקנים.

### Catalog (קטלוג)
רשימת `name` + `description` של כל ה-skills "על המדף". זה כל מה שהמודל רואה מראש.

### Client Application
**המודל לא מגלה skills בכוחות עצמו ולא יודע שהם קיימים.** מישהו צריך לגלות אותם, לערוך קטלוג ולהגיש אותו. ה"מישהו" הוא אפליקציית הקליינט – וזה מה שבונים בפרויקט.

## 🖼️ Progressive Disclosure – לב המנגנון

```text
שלב 1 – Metadata (תמיד נטען)
   name + description של כל ה-Skills המחוברים
   → המודל חושב: האם אחד מהם מתאים למשימה?

שלב 2 – SKILL.md (נטען כשה-skill הופעל)
   תרחישים, נהלים, מתי ואיך להשתמש
   → אם זה לא מספיק, ה-SKILL.md מפנה לקבצים:

שלב 3 – קבצים לפי דרישה
   scripts/ · references/ · assets/
   → נטענים או מורצים רק אם צריך עומק
```

למה זה חשוב: **לא שופכים את כל המומחיות לחלון ההקשר מיד.** עשרה skills בגודל 500 שורות = 5000 שורות בכל שיחה. עם Progressive Disclosure: עשר שורות תיאור + skill אחד כשצריך.

## 📁 מבנה תיקיית Skill

```text
my-skill/
  SKILL.md        ← חובה
  scripts/        ← פעולות להרצה
  references/     ← תיעוד עזר, דוגמאות
  assets/         ← תמונות, תבניות, קבצים סטטיים
```

### SKILL.md – ה-frontmatter

```markdown
---
name: complaint-reply
description: כותבת תשובה בכתב ללקוחה שמתלוננת. השתמשי כשמבקשים לנסח תשובה או מייל ללקוחה כועסת.
---
```

| שדה | חובה? | תפקיד |
|-----|-------|-------|
| `name` | כן | מזהה ייחודי – נכנס לקטלוג |
| `description` | כן | **מתי** להפעיל – זה מה שהמודל קורא כדי להחליט |
| `license`, `compatibility`, `metadata` | לא | רישיון, תאימות, מידע נוסף |
| `allowed-tools` | לא | אילו כלים ה-skill רשאי להפעיל |

> ה-`description` הוא השורה החשובה בקובץ. אם הוא לא אומר *מתי* – ה-skill לעולם לא יופעל.

### איך כותבים את התוכן
- **לשון ציווי:** «השתמש במיומנות זו כאשר…»
- **כוונה, לא מימוש** – מה להשיג, לא כל שורת ביצוע
- **תמציתיות** – כל המוסיף גורע
- **נהלים עדיפים על הצהרות** («בדוק X, אחר כך Y» ולא «היה זהיר»)
- **גמישות מול קשיחות** – לא לסגור כל נתיב; קשיחות רק איפה שטעות עולה ביוקר

### אבני בניין בתוך SKILL.md
| אבן | דוגמה |
|-----|-------|
| **Gotchas** | «לא להבטיח החזר מלא – לא קיים בנהלים» |
| **Templates** | מבנה קבוע לפלט (4 שורות) |
| **Checklists** | `- [ ] יש מספר ימים מפורש` |
| **Validation loops** | בדוק → תקן → בדוק שוב |

**מספר הזהב (אצבע):** ~500 שורות / ~5000 טוקנים ל-SKILL.md. מעבר לזה – מפצלים ל-`references/`.

### scripts/
פעולות אמיתיות שה-skill מפנה אליהן. המודל **לא צריך לדעת מה כתוב בפנים** – רק שכשצריך, מריצים את הפקודה. אפשר לשלב סקריפט בתוך workflow («שלב 3: הרץ `scripts/validate.py`»).

### references/ ו-assets/
`references/` – תיעוד, דוגמאות, נספחים שנטענים רק כשנדרש. `assets/` – תמונות, תבניות קבצים, חומרים ספציפיים.

## 🛠️ Lab / שלבי פיתוח

### שלב 1 – Skill ראשון
כתבו `SKILL.md` למומחיות ממוקדת, למשל: «סיכום מסמך מדיניות לחברת סלולר ב-3 בולטים + סיכונים». ודאו: `description` שאומר *מתי*; מבנה פלט; Checklist.

### שלב 2 – Discovery
**אפליקציית הקליינט** (לא המודל):
1. סורקת את תיקיית ה-skills ומוצאת כל `SKILL.md`
2. מחלצת `name`, `description` ו-`body` מכל קובץ
3. שומרת במערך – **SkillsStore**

```python
def load_skills() -> dict:
    store = {}
    for path in SKILLS_DIR.glob("*/SKILL.md"):
        meta, body = _parse(path.read_text(encoding="utf-8"))
        store[meta["name"]] = {"name": ..., "description": ..., "body": body}
    return store
```

### שלב 3 – Disclose + Activate
מתחילים דווקא מהאמצע:

1. **ה-Tool `activate_skill(name)`** – מקבל שם, מחזיר את ה-`body` מה-SkillsStore.
2. **הקטלוג** – רשימת `name` + `description` בלבד. בוחרים איפה להגיש אותו:
   - ב-**System Prompt**, או
   - ב-**description של ה-tool** (כך בדמו)
3. הנחיה מצורפת: *«אם אחד ה-Skills מתאים למשימה, הפעילי את `activate_skill` כדי לקבל את ההנחיות המלאות.»*

```python
tool = {
  "name": "activate_skill",
  "description": "כשמשימה מתאימה לתיאור של skill, הפעילי אותו לפי השם.\n"
                 "== Skills זמינים ==\n" + catalog,
  "parameters": {"name": {"type": "string"}},
}
```

**המודל מאומן על Tool Calling – אין צורך באימון מיוחד ל-Skills.** לכן כל מודל שיודע לקרוא לכלים יודע לעבוד איתם.

### שלב 4 – Edge cases
- שם skill שלא קיים → מחזירים הודעת שגיאה **עם רשימת השמות הזמינים**, כדי שהמודל יתקן בעצמו.
- ה-skill מפנה ל-`scripts/` → בהחזרת ה-body מוסיפים את **נתיב התיקייה** (כדי שהמודל ידע איפה הסקריפט).
- skills עם `description` חופף → המודל מתלבט. חדדו: *מתי כן* ו*מתי לא*.

### שלב 5 (פרויקט מורחב) – Files-browser agent
אפליקציית Electron של דפדפן קבצים עם צ'אט צד. ממשים `loadSkills` ו-`activate_skill`, בעזרת Anthropic Messages API + Tool Runner SDK.  
`github.com/malbruk/dovrot-ai-projects/tree/master/09-skills/files-browser-agent`  
הגשה: ריפו ציבורי + README (מטרה, הרצה, דוגמה ל-skill שהאייג'נט מזהה ומפעיל).

## 📊 Skills מול MCP

| | **Skills** | **MCP** |
|---|------------|---------|
| מיקום | «בפנים» – ידע / נהלים / סקריפטים | «בחוץ» – שירותים, DB, APIs |
| מטרה | מומחיות ו-workflow | גישה סטנדרטית לכלים חיצוניים |
| טעינה | Progressive Disclosure | list_tools + invoke |
| אנלוגיה | מדריך מומחה על המדף | שקע חשמל אחיד לכל מכשיר |

במערכות אמיתיות משלבים: Skill אומר **איך** לעבוד; MCP נותן **במה** לגעת.

### Skills מול RAG (שיעור 5)
- **RAG** מזריק **ידע** (עובדות מהמאגר) לפי דמיון סמנטי לשאלה.
- **Skill** מזריק **נוהל** (איך לעבוד) לפי התאמה של המודל ל-description.

## 💡 Best Practices

- **רק כשיש מומחיות אמיתית.** לא skill על «להיות נחמד».
- נהלים לפני הצהרות; Gotchas לפני דוגמאות.
- ה-description הוא ה-API: כתבו אותו כמו תיאור של כלי.
- Validation loops: בדוק → תקן → בדוק.
- שמרו על SKILL.md קצר. מה שנדיר – ל-`references/`.
- בדקו עם בקשות שאמורות להפעיל ובקשות שלא אמורות.

## ✅ לסיכום

- Skills אורזים מומחיות קלה-משקל לאייג'נט.
- Progressive Disclosure חוסך Context Window: קטלוג תמיד, SKILL.md כשצריך, קבצים לפי דרישה.
- מאחורי הקלעים: קטלוג + Tool Calling רגיל. לא הוספנו יכולת חדשה למודל – סידרנו לו את שולחן העבודה.
- ה-`description` קובע אם ה-skill יופעל.
- אל תבנו סוכן ענק – בנו מדף skills.

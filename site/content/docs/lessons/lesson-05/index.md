## 🌟 הקדמה

### למה בכלל RAG? האם מודלים יודעים הכל?

לא. המודל:

- אומן על מידע **עד תאריך מסוים**
- לא מכיר **נתונים פרטיים / פנימיים** (מדיניות החברה, מחירון, נהלים)
- מתקשה להתמקד **בגרסה הספציפית שלכם** של המוצר
- כשהוא לא יודע – הוא **ממציא בביטחון** (בדמו: «מגיע לך החזר מלא מיד» במקום «חיוב אחד תוך 5 ימי עסקים»)

**RAG** – מוסיף מידע שלנו לקונטקסט, בזמן אמת, בלי לאמן מחדש.

```text
Retrieval → Augmented → Generation
אחזור      → העשרה      → יצירת תשובה
```

| שלב | מה קורה | מי עושה |
|-----|---------|---------|
| **R**etrieval | מוצאים את המקטעים הרלוונטיים | הקוד שלנו (embedding + חיפוש) |
| **A**ugmented | מזריקים אותם לפרומפט, עם Guardrails | הקוד שלנו (תבנית) |
| **G**eneration | מנסחים תשובה בגבולות ההקשר | ה-LLM / הסוכן |

עד שלב ה-Augmented זה "דומה לחיפוש גוגל". ה-Generation הוא שלב ה-LLM / סוכן.

> **משפט עוגן:** RAG = המודל לא יודע. אנחנו מביאות לו את המקור, ו-Guardrails מחזיקים אותו בתוכו.

## 📌 מושגים ועקרונות

### Offline מול Runtime
- **Offline** – לפני שמישהי שואלת: איסוף → חיתוך → embedding → אינדקס. עולה זמן וכסף **פעם אחת**.
- **Runtime** – בכל שאלה: embedding לשאלה → חיפוש → פרומפט → LLM → תשובה.

### אותו מודל Embedding
השאלה והמאגר חייבים להיות באותו מודל – אחרת הוקטורים חיים ב"אולמות" שונים והמרחק חסר משמעות.

### Guardrails
משפט בפרומפט שמגדיר **מה אסור**: «רק מההקשר», «אל תשתמשי בידע קודם», «אם אין מידע – עני בדיוק X». בלעדיו המודל משלים מהזיכרון.

### Threshold (סף)
ציון cosine מינימלי שמתחתיו מקטע לא נחשב רלוונטי. בלי סף, top-K תמיד מחזיר *משהו* – גם לשאלה על מזג אוויר.

### Context Rot
יותר הקשר ≠ תשובה טובה יותר. top-K גדול מדי מוסיף רעש ומקשה על המודל.

## 🖼️ זרימת RAG

### שלב הכנה (Offline / לפני ריצת הסוכן)

```text
🧩 איסוף  →  ✂️ Chunking (+ניקוי)  →  🧠 Embeddings  →  🗂️ שמירת וקטורים (`.npy`; ובקנה מידה גדול Vector DB)
```

### Runtime

```text
שאלה מהמשתמש
  → האם דורשת מידע?
      לא → Prompt בסיסי
      כן → בחירת מקור: Vector DB / SQL / אינטרנט / API
           → בניית Prompt עם הקשר + שאלה
  → LLM
  → Post-processing
  → תשובה למשתמש
```

> «האם דורשת מידע?» – שאלה כללית («מה זה API?») המודל יודע לבד. שאלה על מידע פנימי («איך מגדירים חיבור ב-API של החברה?») דורשת RAG.

## 🛠️ שלבי Lab

### שלב 1 – Dataset
- תחום ממוקד («שירות לקוחות בסלולר»).
- 30–50 שאלות ותשובות. אפשר לייצר עם LLM («תן לי 50 שאלות ותשובות נפוצות בשירות לקוחות בתחום X»), **אבל את עורכת**: תשובות עם פרטים אמיתיים (מספרים, ימים, שמות כפתורים).
- שומרות כ-JSON/CSV עם שני שדות בלבד: `question`, `answer`.
- אופציונלי: העלאה ל-Hugging Face – גישה שיתופית, ספריית `datasets`, גרסאות.

### שלב 2 – Embeddings
- לולאה על השאלות (עדיף **batch** – פחות קריאות).
- אותו מודל לכל האינדקס והשאילתות. רשמי את שם המודל וגרסתו.
- שמירת מיפוי `index_id → answer`.

```python
# סקיצה – Cohere
co = cohere.Client(API_KEY)
vectors = co.embed(
    texts=questions,
    model="embed-multilingual-v3.0",   # תומך עברית
    input_type="search_document",
).embeddings
```

### שלב 3 – שמירת הווקטורים
- נרמול כל וקטור לאורך 1: אחרי נרמול, מכפלה פנימית = דמיון cosine.
- שמירה ל-`.npy`, כדי לא לחשב embeddings מחדש בכל הרצה.

```python
import numpy as np

matrix = np.array(vectors, dtype=np.float32)
matrix /= np.linalg.norm(matrix, axis=1, keepdims=True)
np.save("qa.npy", matrix)
```

### שלב 4 – Query path
- embedding לשאלה חדשה (אותו מודל, `input_type="search_query"` ב-Cohere).
- חיפוש N שכנים (3–5) והמרת מרחק לציון.
- סינון לפי **סף**.
- בניית הקשר מהתשובות (ואפשר גם מהשאלה המקורית שנשלפה).

```python
q = np.array(query_vec, dtype=np.float32)
q /= np.linalg.norm(q)
sims = matrix @ q                      # cosine לכל שאלה במאגר
top = np.argsort(-sims)[:3]
hits = [(answers[i], float(sims[i])) for i in top]
hits = [h for h in hits if h[1] >= MIN_SCORE]
```

### שלב 5 – Prompt + Guardrails

```text
את/ה עוזר/ת מומחה/ית. ענה על שאלת המשתמש בהתבסס *אך ורק* על ההקשר.

הקשר:
---

[...]

- השתמש רק בהקשר

- אל תשתמש בידע קודם

```

### שלב 6 – Gradio
ממשק: תיבת שאלה + הצגת תשובה. מומלץ להוסיף **מקורות וציון דמיון** – שקיפות למשתמשת (ולכן גם בדמו).

### שלב 7 – Edge cases
- אין מקטע מעל הסף → הפרומפט עדיין נשלח, ה-Guardrail אחראי על «אין מספיק מידע».
- שאלה בעברית על מאגר אנגלי (או להפך) → מודל embedding רב-לשוני.
- שאלה עם שני חלקים → שקלי לפרק לשתי שאילתות.

## ⚠️ אתגרי RAG – שלב אחר שלב

> לא צריך לפתור הכל בפרויקט 1. צריך **לדעת איפה זה נשבר**.

### 1. איסוף נתונים
| אתגר | פתרון |
|------|-------|
| פורמטים שונים (PDF, DOCX, HTML, MD, CSV) | ספריות ייעודיות (`pdfplumber`, `python-docx`, `BeautifulSoup`) + שכבת עטיפה אחידה |
| טקסט מלוכלך (כותרות, שורות ריקות, קידודים) | Preprocessing, Normalize, זיהוי שפה |
| מידע אישי / זכויות יוצרים | PII detection (Presidio), מדיניות איסוף |
| עדכניות | `timestamp` לכל מקור + רענון תקופתי |
| נפח גדול | batch, עיבוד מקבילי, ענן |

### 2. Chunking
| אתגר | פתרון |
|------|-------|
| גודל לא נכון (קצר = חסר הקשר, ארוך = רעש) | ניסוי: 200–500 טוקנים; חפיפה (overlap) |
| שבירה עיוורת באמצע משפט / קוד | חלוקה לפי כותרות / פסקאות / Markdown |
| שאלה שנפרסת על שני מקטעים | קישור למקטעים סמוכים + היררכיה (פרק → סעיף) |
| אין מידע על המקור | **metadata** בכל chunk |

```json
{"content": "הטקסט", "source": "user_guide.pdf", "section": "2.1", "page": 3}
```

### 3. Embeddings
- בחירת מודל לפי **שפה** (עברית?), תחום (קוד / משפטים) ואורך המקטעים.
- טקסט קצר מדי לא מייצג הקשר; ארוך מדי נחתך (truncation).
- רשמי גרסת מודל – שדרוג מודל = אינדקס חדש.
- עלות: batch, חישוב offline, שמירה ל-DB; לחילופין מודל מקומי.
- אל תשאירי embedding «יתום» – שמרי `chunk_id` + metadata.

### 4. Vector DB
- כל רשומה: `id` + `vector` + `metadata` + טקסט (או מזהה לטקסט).
- עדכון / מחיקה: `document_id` לכל קבוצת chunks, שדה `version`, תמיכה ב-upsert/delete.
- מאות אלפי פריטים ומעלה → ANN + sharding.
- אבטחה: namespaces / multi-tenant, הרשאות, הצפנה.

### 5. קלט המשתמש
| אתגר | פתרון |
|------|-------|
| «איך זה עובד?» – כללי מדי | LLM שמחדד את השאלה; «התכוונת ל…?» |
| עברית/אנגלית מעורבב, שגיאות כתיב | זיהוי שפה, normalize |
| שאלה בשני חלקים | Question decomposition |
| «ומה לגבי מה שציינת קודם?» | היסטוריית שיחה / memory |
| המשתמשת לא יודעת איך לשאול | שאלות המשך מוצעות |

### 6. החלטה: האם צריך מידע חיצוני?
- שופט מקדים (LLM): «האם לענות על השאלה צריך מידע חיצוני?» או חוקים פשוטים («לפי התיעוד»).
- איזון מהירות/דיוק: classifier זריז לפני חיפוש.
- אחרי שליפה: ציון נמוך → לא להשתמש בהקשר (**fallback** למודל או הודעה).
- שקיפות: להציג «מבצע חיפוש על המסמכים…», toggle להפעלה/כיבוי.

### 7. שליפה מ-Vector DB
| אתגר | פתרון |
|------|-------|
| כמה לשלוף? | `top_k` 3–5 + `threshold` |
| מקטעים «קרובים» במילים אך לא רלוונטיים | **re-ranking** |
| אין תוצאה | Fallback + הודעה ברורה |
| קטעים סותרים | סימון מקור + הוראה להדגיש סתירה |
| הרשאות | סינון לפי metadata |
| ביצועים | אינדקס נכון, caching |

### 8. מקורות אחרים (למבט על)
- **SQL:** Text-to-SQL עם סכימה בפרומפט. **לעולם לא להריץ raw SQL** – משתמש עם הרשאות קריאה בלבד, שאילתות מבוקרות (SQL injection). לתרגם תוצאה למשפט: «יש 12 תלונות פתוחות».
- **אינטרנט:** שכתוב השאלה לשאילתת חיפוש, סינון אתרים אמינים, APIs כמו Serper/Tavily (חוזרים בשיעור 10).
- **API:** wrapper אחיד, מפתחות במשתני סביבה, caching, retry / circuit breaker.

### 9. בניית הפרומפט
- מידע ממקורות שונים → נרמול לפורמט אחיד, **הפרדה ברורה** בין מקורות.
- סתירות → «לפי המסמכים / לפי ה-API», הוראה להדגיש סתירה.
- גבול טוקנים → סינון קפדני, סיכום מידע ארוך.

```text
להלן מידע שנאסף ממקורות שונים לשאלה: "איך להגדיר גיבוי אוטומטי?"

[מקטע ממסמכי Vector DB]  ...
[תוצאות SQL DB]          | backup_enabled | last_backup_date | ...
[תוצאות API]             {"backupStatus": "active", ...}

השתמש במידע זה כדי לענות באופן מדויק. אם יש סתירות, הדגש זאת. אל תמציא מידע.
```

### 10. Post-processing
- **Hallucination check:** האם הטענה בתשובה קיימת בהקשר?
- סריקת PII ו-content moderation.
- התאמת פורמט (Markdown / JSON – חיבור לשיעור 2).
- **Citations:** ציון מקור ליד כל טענה.

**הדרך הנכונה:** לבנות suite של שאלות-תשובות צפויות (תשובה שאת מצפה לה + המקור שאמור להישלף) → לשפר chunk / סף / פרומפט לפי כשלונות, לא לפי תחושת בטן.

## 💡 טיפים ו-Gotchas

- **Data קטן ומדויק** חזק יותר ממסמכים ענקיים ומלוכלכים.
- שמרו על אורך פרומפט – top-K גדול מדי = Context Rot.
- הציגו ציון דמיון ליד כל מקור (שקיפות, וגם דרך לכוון את הסף).
- תמיד בדקו שאלת **מחוץ לתחום** – זו הבדיקה היחידה שמוכיחה שה-Guardrails עובדים.
- אם הסף גבוה מדי – «לא מצאתי» גם על שאלות טובות. נמוך מדי – הקשר לא רלוונטי נכנס. כוונו לפי הבדיקות.
- Ollama / מודלים מקומיים – טובים ל-lab בלי עלות API.

## ✅ לסיכום

- RAG = Retrieval + Augment + Generate סביב ידע שלכם.
- הכנה Offline מול שאילתא ב-Runtime.
- Embeddings + דמיון cosine = ליבת החיפוש; LLM = ניסוח בגבולות ההקשר.
- הסף והפרומפט (Guardrails) הם מה שעוצר המצאה.
- לכל שלב בצנרת יש אתגרים – מודדים ב-suite בדיקות, לא בתחושה.
- עכשיו יש לכם את כל הכלים ל-**פרויקט 1**.

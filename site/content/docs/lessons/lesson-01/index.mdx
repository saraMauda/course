## 🌟 הקדמה

הטמעת מודלי שפה גדולים (LLMs) במערכות תוכנה יוצרת שינוי עמוק באופן שבו מפתחים מתכננים, בונים ומפעילים מערכות. במקום קוד דטרמיניסטי שכל תוצאתו צפויה מראש, מתווסף כעת רכיב הסתברותי, יצירתי וגמיש.

השינוי הזה מאפשר ממשקים טבעיים ועשירים יותר, אך במקביל מחייב חשיבה חדשה על בקרה, הקשר, ואחריות. בשיעור הזה נבנה את השפה המשותפת של כל הקורס: מ-ML קלאסי דרך טוקנים וחלון הקשר, ועד ל-Function Calling – המנגנון שמאפשר למודל "לבקש" פעולות בעולם האמיתי.

---

## 🆕 מה השתנה: ML קלאסי מול LLM

| | ML קלאסי | LLM |
|---|----------|-----|
| קלט | פיצ'רים מספריים / טבלאיים | טקסט (טוקנים) |
| משימה | סיווג / רגרסיה / אשכולות | הבנה + ייצור שפה + כלים |
| פלט | צפוי יחסית | הסתברותי – אותה שאלה, תשובות שונות |
| עדכון ידע | אימון מחדש | פרומפט, RAG, Tools, (לפעמים Fine-Tuning) |
| אינטראקציה | API / כפתורים | שפה טבעית + Function Calling |

**שורה תחתונה:** LLM הוא לא "מודל ML עוד אחד" – הוא רכיב מערכת שדורש **הנדסת הקשר** (context engineering), לא רק אימון.

---

## 📌 מושגים ועקרונות

### Machine Learning → Neural Networks → NLP → Transformers → LLM

- **Machine Learning** – מערכות שלומדות מדפוסים בנתונים במקום כללים ידניים בלבד.
- **Neural Network** – רשת שכבות שמקבלת ייצוגים ומפיקה חיזויים.
- **NLP** – עיבוד שפה טבעית: הבנה, תרגום, סיווג, סיכום.
- **Transformers** – ארכיטקטורה מבוססת Attention; הבסיס ל-GPT, Claude, Gemini וכו'.
- **LLM / Foundation Model** – מודל שפה גדול שאומן על כמויות עצומות של טקסט ומשמש כ"בסיס" ליישומים.

בקורס **לא** נצלול למתמטיקה של Attention – מספיק להבין: המודל מנבא את **הטוקן הבא** בהסתברות, בהתבסס על ההקשר שקיבל.

### Token, Prediction, Prompt

| מושג | משמעות |
|------|--------|
| **Token** | יחידת עיבוד של המודל (חלק ממילה / מילה / סימן) |
| **Prediction** | בחירת הטוקן הבא לפי התפלגות |
| **Prompt** | ההנחיה + ההקשר שנשלחים למודל |
| **Context Window** | כמה טוקנים המודל "רואה" בקריאה אחת |

### Context Window ו-Context Rot (רקבון הקשר)

חלון ההקשר הוא מוגבל. ככל שמטעינים יותר היסטוריה, כלים, מסמכים ותוצאות – האיכות עלולה **ליפול**, לא רק "להתרוקן":

- המודל מתחיל להתעלם מהוראות מוקדמות
- עולה הסיכוי להזיות ולסתירות
- העלות וה-latency עולים

**Context Rot** = ככל שההקשר ארוך ומלוכלך יותר, הסיכוי שהמודל יתנהג נכון יורד.  
לאורך הקורס נלמד פתרונות: חלוקה (chunking), RAG, Skills (Progressive Disclosure), Trim/Summarize, וניהול State.

### API מול צ'אט

- **API "יבש"** – שולחים הודעה, מקבלים השלמה. אין כלים, אין זיכרון מערכת, אין לולאה.
- **צ'אט / Agent** – יש לולאה, יש Tools, יש (לעיתים) זיכרון ו-Harness.

הפתרון שמחבר ביניהם: **Function Calling** – המודל לא מריץ קוד בעצמו, אבל יודע **לבקש** הפעלה של פונקציה עם פרמטרים.

## 🖼️ Function Calling – הזרימה מאחורי הקלעים

![Function Calling Flow](/assets/function-calling-flow.svg)

<Mermaid chart={"flowchart LR\n  User -->|Query| Bot\n  Bot -->|Query_plus_Tools| Model\n  Model -->|ToolCall| Bot\n  Bot -->|RunTool| World[External_Tool]\n  World -->|Result| Bot\n  Bot -->|Query_Call_Result| Model\n  Model -->|Completion| Bot\n  Bot -->|Response| User"} />

| שלב | מי | מה קורה |
|-----|----|---------|
| 1 | User → Bot | **Query** – בקשת המשתמש. ה-Tools עדיין רק **מוגדרים** בפרומפט (לא הופעלו) |
| 2 | Bot → Model | **Query + Tool definitions** – המודל מחליט *האם* ואיזו פונקציה להפעיל |
| 3 | Model → Bot | **Tool Call** – שם הפונקציה + פרמטרים. המערכת **מריצה** את הקוד |
| 4 | Bot → Model | **Query + Tool Call + Result** – התוצאה האמיתית חוזרת למודל |
| 5 | Model → Bot | **Completion** – תשובה בשפה טבעית |
| 6 | Bot → User | **Response** |

> **נקודת מפתח:** ה-LLM **לא** מריץ את הפונקציה. הוא בוחר *מה* להריץ; **ה-Host / הקוד שלנו** מבצעים ולוחצים את התוצאה חזרה.

## 🛠️ שלבי פיתוח / Demo

### שלב 1 – שיחה "סתם" בלי כלים
שולחים למודל: *"מה מזג האוויר בתל אביב?"*  
בלי tools – המודל **ממציא** או מתנצל. רואים את הגבול.

### שלב 2 – הגדרת Tool
מגדירים סכימה (שם, תיאור, פרמטרים), למשל:

```text
name: get_weather
description: מחזיר מזג אוויר למיקום נתון
parameters: { location: string }
```

### שלב 3 – לולאת Tool Call
1. קריאה ראשונה למודל + רשימת tools  
2. אם חוזר `tool_use` → מריצים את הפונקציה  
3. מחזירים את התוצאה למודל  
4. מקבלים תשובה סופית למשתמש  

### שלב 4 – דיון ארכיטקטוני
איפה ישמרו ההגדרות? מי מבצע? מה קורה כשכלי נכשל?  
(חימום ל-MCP בשיעור 7 ול-Harness בשיעור 9)

## 💡 טיפים ו-Gotchas

- **Temperature נמוך** (למשל 0) → עקביות; גבוה → יצירתיות. למערכות production – לרוב נמוך.
- **תיאור ה-tool** הוא חלק מהפרומפט – תיאור גרוע = בחירת כלי גרועה.
- Function Calling **לא** מחליף RAG: כלי מושך נתונים/פעולות; RAG מזרים **ידע** לפרומפט.
- Context Window הוא תקציב – כל tool result תופס טוקנים (Context Rot).

---

## ✅ לסיכום

- LLM מוסיף רכיב **הסתברותי** למערכת – נדרשים בקרה והנדסת הקשר.
- המודל עובד ב**טוקנים** בתוך **Context Window** מוגבל.
- **Context Rot** מחייב תכנון: לא "לשפוך הכל" לפרומפט.
- **Function Calling** הוא הגשר בין "מוח" (מודל) ל"ידיים" (קוד).
- כל מה שנבנה בהמשך (RAG, Agents, MCP, LangGraph) יושב על היסודות האלה.

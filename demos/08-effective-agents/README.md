# דמו שיעור 08 – Workflows ו-Agents

אותה הודעה, ארבע תבניות. רואים את התשובה, **מי שולט בזרימה**, **כמה קריאות למודל** זה עלה, את כל הפרומפטים שנשלחו, ואת מה שקרה מאחורי הקלעים.

משפט עוגן:

> **Workflow – הקוד שולט בנתיב. Agent – המודל שולט בנתיב. מתחילות ב-Workflow.**

חיבור לשיעור 03: ה-Agent כאן הוא אותה לולאת ReAct. כאן משווים אותה למה שהקוד יכול לעשות לבד.
חיבור לשיעור 07: אותן פעולות (חשבון, מדיניות), רק שהפעם הקוד מחליט מתי לקרוא להן.
חיבור לשיעור 05: ה-Evaluator הוא אותה בדיקה של «האם התשובה נאמנה לנתונים», רק בתוך הלולאה.

## הרצה

```bash
cd demos/08-effective-agents
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```

שימי מפתח ב-`.env`, ואז לחיצה כפולה על `הרצה.bat` או:

```bash
python app.py
```

בחלון: כותבות הודעה (או לוחצות על דוגמה) → בוחרות **תבנית** → **שלחי**.

מתחת לתיבה יש ארבע דוגמאות מ-`prompt.py`: חיוב, הזמנה, מחוץ לתחום, וחיוב **בלי מספר לקוח**.

אם OpenAI חסום (רימון), הקוד עובר לבד להדגמה מקומית או ל-Gemini. פירוט ב-`.env.example`.

> **שימי לב:** בהדגמה המקומית (מצב `mock`) התשובות מדומות כדי להראות את הדפוס. למשל ב-Evaluator–Optimizer הסבב הראשון תמיד נכשל. עם מודל אמיתי המספרים ישתנו (מודל טוב יעבור כבר בסבב 1). זו בדיוק הסיבה שיש תקרת סבבים.

## הקבצים להראות בכיתה (בסדר הזה)

| קובץ | מה יש בו |
|------|----------|
| `prompt.py` | כל הפרומפטים. כל תפקיד מתחיל בתגית: `[AGENT]`, `[ROUTER]`, `[WORKER]`, `[EVALUATOR]`... |
| `tools.py` | המידע והפעולות. המודל לא נכנס לכאן |
| `agent.py` | **המודל שולט**: לולאת ReAct. אין נתיב קבוע |
| `workflows.py` | **הקוד שולט**: Routing, Parallelization, Evaluator–Optimizer. הנתיב כתוב בפייתון |
| `ask_the_model.py` | הבחירה: אותה הודעה, ארבעה מסלולים |
| `app.py` | החלון: הודעה, תשובה, מי שולט, פרומפטים, מה קרה |

`recorder.py` סופר קריאות ומתעד. `llm_client.py` הוא חיבור טכני (OpenAI / Gemini / הדגמה מקומית). לא חובה לפתוח בכיתה.

> **Orchestrator–Workers** לא מומש בדמו. מסבירים בקול (ראי למטה).

## מה להגיד בכל תבנית

התחילי עם הדוגמה הראשונה (חיוב כפול, לקוח 312) וחזרי עליה בכל תבנית. אחר כך החליפי הודעה.

1. **Agent** – ב«מה קרה»: המודל בחר `lookup_account`, אחר כך `lookup_policy`, אחר כך `finish`. **3 קריאות.** «לא ידענו מראש כמה צעדים ובאיזה סדר.» זה כוח, וזה גם חוסר צפיות.
2. **Routing** – `workflows.py`, `run_routing`. המודל מסווג **מילה אחת**. מכאן **הקוד** שולף ומריץ. המודל חוזר רק לנסח. **2 קריאות.** «הנתיב קבוע, אפשר לבדוק אותו, ואין סיכוי שהמודל ישכח לבדוק מדיניות.»
3. **Routing, «מה מזג האוויר?»** – קריאה **אחת**. הקוד ענה תשובה קבועה. ב-Agent אותה הודעה עלתה גם קריאה אחת, אבל ב-Routing זה מובטח על ידי הקוד ולא תלוי בשיקול דעת.
4. **Routing, «למה חויבתי פעמיים?» (בלי מספר)** – הקוד מבקש מספר. **בלי מודל בכלל לצעד הזה.** «כלל פשוט שאפשר לכתוב בקוד – לא משלמים עליו טוקנים.»
5. **Parallelization** – שלוש חוקרות (חשבון, מדיניות, הזמנות) רצות **באותו זמן**, ומאחד אחד ממזג. **4 קריאות**, גם על «מזג אוויר». ב«מה קרה»: «הזמנות → אין מידע». «מתאים כשהמקורות עצמאיים ובאמת צריך את כולם. כאן זה בזבוז, ולכן Routing עדיף. בלי מאחד טוב מקבלים סתירות.»
6. **Evaluator–Optimizer** – ב«מה קרה»: סבב 1, טיוטה גרועה. המעריכה נכשלת עם **משוב**. סבב 2, תיקון, עבר. **4 קריאות.** «המחוללת לא ראתה את הקריטריונים. רק המעריכה.» פתחי את `EVALUATOR_CRITERIA` ו-`MAX_ROUNDS` ב-`prompt.py`: «בלי תקרה, מעריכה חלשה היא לולאה אינסופית.»
7. **סיכום מול הטבלה** – אותה הודעה, אותה תשובה בערך, **מספר קריאות שונה** ומי שולט שונה. זו ההבחנה כולה.

## Orchestrator–Workers (בקול, בלי קוד)

מנהל (מודל) מפרק משימה לתת-משימות, **שהוא מחליט עליהן בזמן ריצה**, שולח לעובדים, ומרכיב. ההבדל מ-Parallelization: שם הקוד יודע מראש מי העובדים. כאן המודל קובע כמה ואילו. דוגמה: «הוסף פיצ'ר» → קוד, בדיקות, תיעוד.

## שאלות לדיון

- מתי הייתם בוחרות Agent מלא, ולא Routing? ← כשהמרחב פתוח ואי אפשר לחזות מסלולים (מחקר, תקלות מגוונות).
- מה הסיכון ב-Evaluator? ← מעריכה חלשה או קריטריון לא ברור = לולאה, או אישור של תשובה גרועה. לכן תקרת סבבים.
- למה Routing לא ענה על «מה מזג האוויר» דרך מודל נוסף? ← כי לא צריך. שיקול עלות.
- איזו תבנית כל אחד מהמוצרים שלכן? ← פרויקט 1 (Routing?), פרויקט 2 (Agent + Parallel?).
